## 已確認問題

### F01 · P1 · 刪除巢狀 GGUF 會刪掉共同上層目錄內的其他模型

位置：[src/llamacpp/manager.go](/Users/vader/Codes/Go/LlamaLoader/src/llamacpp/manager.go:2165)

`DeleteStoredModel` 取模型相對路徑的**第一個**斜線之前的部分，再對該目錄執行 `os.RemoveAll`。例如刪除 `family/model-a/a.gguf`，實際刪除的是整個 `family`，包含 `family/model-b/b.gguf`。這與掃描器允許任意深度子目錄的行為不一致。

已使用兩份最小合法 GGUF metadata 重現：刪除 A 回傳成功，B 隨之消失。前端雖提示刪除「此模型的完整目錄」，卻未揭示實際刪除的是更高層的共同分類目錄。

修正方向：用明確的模型套件所有權／manifest 決定可刪除範圍。無法證明目錄專屬於該模型時，只刪除選定檔案及已確認的附屬資產；不能以路徑第一段推定所有權。

### F02 · P1 · 合法的非整 byte CIDR 白名單會使 mlx-server 崩潰

位置：[AccessControl.swift](/Users/vader/Codes/Go/LlamaLoader/mlx-server/Sources/MLXServer/AccessControl.swift:207)

`UInt8(0xff << (8 - remainingBits))` 先得到超過 UInt8 範圍的整數，再進行會檢查範圍的轉型。只要前綴長度不是 8 的倍數，且先前完整 byte 比對相符，就會 trap，無法回傳拒絕或允許結果。

以**完整原始 RuntimeAccessControl 類別**及臨時政策檔執行：`127.0.0.0/24` 配對 `127.0.0.1` 正常允許；改用 `/25` 或 `/31` 直接以 signal 5 結束，訊息為 `Not enough bits to represent the passed value`。IPv6 非整 byte 前綴亦使用同一段運算。C++ 版本使用截斷轉型，沒有這個 Swift 特有的陷阱。

修正方向：在 UInt8 型別內建立遮罩，或明確採用正確的截斷運算；加入 IPv4 0–32 與 IPv6 0–128 前綴的邊界測試，核對兩個 Runtime 的結果。

### F03 · P1 · 管理服務關閉逾時後會留下仍在執行的模型程序

位置：[main.go](/Users/vader/Codes/Go/LlamaLoader/src/cmd/llamaloader/main.go:251)

`httpServer.Shutdown` 發生 deadline exceeded 時直接 return，後面的 `llama.Shutdown` 不會執行。HTTP handler 的請求 context 也沒有因 service context 結束而統一取消，因此 Prefill、長生成或緩慢客戶端可讓關閉等待超過 15 秒。

已執行獨立編譯的管理服務及模擬模型 HTTP 子程序：開始對話後向管理服務送 SIGTERM，管理服務在 **15.0 秒後 exit 1，模型子程序仍存活**。測試結束已終止該模擬程序。

修正方向：將所有子程序清理放入必定執行的流程，HTTP 與 Runtime 使用各自合理的關閉期限；逾時後仍要取消請求、關閉連線並終止子程序，最後才彙總錯誤。

### F04 · P1 · Linux ZIP 更新未驗證發布來源，就執行套件內的 install.sh

位置：[manager.go](/Users/vader/Codes/Go/LlamaLoader/src/appupdate/manager.go:341)、[apply.go](/Users/vader/Codes/Go/LlamaLoader/src/appupdate/apply.go:66)

目前檢查 ZIP 路徑、大小、必要檔案、平台及 `BUILD_INFO.txt` 的自述內容，沒有可信的簽章或外部可信摘要驗證。結構符合即可顯示「更新套件已驗證」，接著執行套件提供的安裝腳本。攻擊者也能自行產生 ZIP CRC，因此解壓驗證不能證明發布者。

已在暫存目錄建立未簽章套件並任意替換 `install.sh`，`extractAndValidate` 仍接受。**只驗證解壓／檢查結果，未執行替換後的安裝腳本。**

此問題需要已登入的管理者上傳遭替換或來源不可信的套件，不是未登入上傳繞過。修正方向：在任何套件程式執行前，以固定信任根驗證簽章及完整檔案清單；將「結構檢查」與「官方來源驗證」在狀態及 UI 上分開。

### F05 · P1 · 記憶體保護以尚未套用本次開關的 KV 模式估算

位置：[manager.go](/Users/vader/Codes/Go/LlamaLoader/src/llamacpp/manager.go:113)、[memory_pressure.go](/Users/vader/Codes/Go/LlamaLoader/src/llamacpp/memory_pressure.go:222)

`Start` 先呼叫記憶體保護，之後才依本次 `kv_cache_quantization_enabled=false` 將 Profile 的 Q4／Q8 改為未量化。結果是實際關閉 KV 量化，保護機制卻仍套用量化後的折減係數。

已使用 8 GiB 稀疏模型檔、32 GiB 總記憶體／20 GiB 可用記憶體的模擬快照及假 Runtime 重現。Context 131072 被放行；回報估算為 **17,090,294,579 bytes**，但同一套公式按實際未量化模式計算為 **29,287,592,755 bytes**，超過可用的 **21,474,836,480 bytes**。本測試未實際配置該數量 GPU 記憶體。

修正方向：先將 Profile、本次開關與互斥條件解析成唯一的有效啟動配置，再由記憶體估算、參數產生及狀態保存共同使用，避免各階段看到不同模式。

### F06 · P2 · 未量化 MLX 的 Context Size 與保護降級沒有傳給 Runtime

位置：[manager.go](/Users/vader/Codes/Go/LlamaLoader/src/llamacpp/manager.go:520)、[MLXRuntime.swift](/Users/vader/Codes/Go/LlamaLoader/mlx-server/Sources/MLXServer/MLXRuntime.swift:43)

Go 只有在啟用 KV 量化且沒有外部 Draft 時才傳 `--max-kv-size`。Swift 的有效上下文則取模型 metadata 與 `configuration.maxKVSize` 的較小值，沒有獨立的受管請求上下文參數。

已透過假 mlx-server 捕捉實際啟動 argv：設定 ContextSize=512、模型 metadata 上限 131072、關閉 KV 量化，argv 完全沒有 512 或其他對應上下文限制。因此 UI／狀態顯示的 Context，以及記憶體保護宣告的 Context 降級，不一定是 Runtime 實際採用的請求上限。

修正方向：將「請求上下文上限」與「rotating KV cache 大小」分開傳遞，讓一般、DFlash、MTP 及量化模式都受相同上限約束；不宜直接強加 rotating cache 而破壞推測解碼。

### F07 · P2 · 記住我的登入憑證在登出後仍可重用

位置：[store.go](/Users/vader/Codes/Go/LlamaLoader/src/session/store.go:80)、[store.go](/Users/vader/Codes/Go/LlamaLoader/src/session/store.go:115)

`Logout` 只刪除記憶體 session map 項目並要求瀏覽器清除 Cookie；持久 Cookie 從未加入該 map，而是每次以帳密衍生金鑰驗證簽章。登出不會撤銷這個 token。

已重現：勾選記住我登入、保存測試 Cookie、登出，再把相同 Cookie 傳給 `Authenticated`，結果仍為 true。一般瀏覽器 UI 登出能回到登入頁，但已複製的持久憑證仍有效，直到到期或帳密變更。

修正方向：為持久憑證加入可撤銷的伺服器端識別或撤銷紀錄，並維持重啟後的撤銷語意；回歸測試應涵蓋一般及持久兩種 Cookie。

### F08 · P2 · 新版更新程序啟動即失敗，仍會被判定完成

位置：[apply.go](/Users/vader/Codes/Go/LlamaLoader/src/appupdate/apply.go:174)、[apply.go](/Users/vader/Codes/Go/LlamaLoader/src/appupdate/apply.go:144)

`launchTarget` 只呼叫 `command.Start`，隨即 Release；成功建立程序不代表程式完成初始化、讀取設定或綁定監聽埠。上層直接寫入 completed，既有 rollback 分支只處理連程序都無法啟動的錯誤。

已用內容為 `exit 42` 的臨時 run.sh 重現：`launchTarget` 回傳 nil。完整 Linux 替換／回復流程未在本機執行，但這個失效判定函式已直接驗證。

修正方向：在合理期限內取得新版實例的啟動確認與健康狀態，同時追蹤提前退出；確認前保持可回復狀態，失敗時執行 rollback，成功後才寫 completed。

### F09 · P2 · 下載路徑的 SafeJoin 無法阻止父目錄符號連結跳出模型根目錄

位置：[manager.go](/Users/vader/Codes/Go/LlamaLoader/src/download/manager.go:1715)、[manager.go](/Users/vader/Codes/Go/LlamaLoader/src/download/manager.go:1306)

`SafeJoin` 只檢查字串清理及 `filepath.Rel`；後續 MkdirAll、OpenFile 與 Rename 會沿用既有的父目錄符號連結，沒有以實際 filesystem root 限制寫入位置。

已建立 `models/linked -> outside`，使用原始下載 Manager 及本機 HTTP fixture 下載，檔案確實落在 outside。這需要模型根目錄中已存在可利用的符號連結；未宣稱遠端下載者可憑空建立符號連結。

修正方向：建立共用的受限目錄 I/O 層，在實際開檔及替換時保證仍位於模型 root 內；單純先 EvalSymlinks、再用原字串開檔仍需考慮競態。

### F10 · P2 · MLX 圖片 URL 可以存取服務主機本機檔案與內網

位置：[MLXRuntime.swift](/Users/vader/Codes/Go/LlamaLoader/mlx-server/Sources/MLXServer/MLXRuntime.swift:663)

來自 API 的 `image_url` 可直接指定 `file://`、服務主機上的既存路徑，或任意 http／https URL。沒有模型目錄／圖片目錄限制、內網目的地政策或 redirect 後的目的地驗證。持有推論 API 使用權限，不應自動代表可以存取服務主機全部可讀取的圖片與內部 HTTP 資源。

已將原始 resolveImage／persistTemporaryImage 方法放入獨立 Swift harness：本機 file URL 被接受，loopback HTTP fixture 實際收到請求。沒有讀取真實私密檔案、存取其他內網主機，亦未以 VLM 驗證圖片內容外洩；確認的是輸入參照與連線邊界缺失。

修正方向：為遠端 API 定義明確的圖片來源政策。預設拒絕伺服器本機路徑，或僅允許受限的上傳識別；HTTP 來源依部署用途允許，並於 DNS 解析與每次重新導向後重新檢查。

### F11 · P2 · 遠端圖片大小限制在整份回應載入記憶體後才執行

位置：[MLXRuntime.swift](/Users/vader/Codes/Go/LlamaLoader/mlx-server/Sources/MLXServer/MLXRuntime.swift:675)、[MLXRuntime.swift](/Users/vader/Codes/Go/LlamaLoader/mlx-server/Sources/MLXServer/MLXRuntime.swift:687)

`URLSession.shared.data(from:)` 先收完整遠端內容，再於 persistTemporaryImage 檢查預設 25 MiB 限制。只有短 URL 的 API 請求不會受 32 MiB request body 上限有效保護；大型或持續回傳的遠端內容仍可先消耗大量記憶體。

原方法 harness 將限制縮小為 1 KiB，本機端點回傳 64 KiB；結果是完整接收 65,536 bytes 後才回報 imageTooLarge。未以超大實際流量測試 OOM。

修正方向：採有累計上限的串流讀取，在讀到上限加一時立即取消，並配置合理時間限制。Content-Length 可提早拒絕，但不能取代實際位元組計數檢查。

### F12 · P2 · 畸形 Fast GGUF 的 offset 可在驗證階段造成整數溢位崩潰

位置：[FastGGUFContainer.swift](/Users/vader/Codes/Go/LlamaLoader/mlx-server/Sources/MLXServer/FastGGUFContainer.swift:278)

解析器先計算 `payloadOffset + tensor.offset` 及 `start + storedBytes`，再檢查檔案範圍。惡意或損毀 header 的 offset 可以是 Int64.max；普通加法會先 trap，無法走既有的 invalidTensor error／快取失效處理。

已新增臨時 XCTest 直接呼叫原始 `FastGGUFContainer.load`，建立約 1 MiB 的容器、offset=Int64.max、合法的一個 U8 tensor 描述。預期拋出錯誤，實際測試程序以 **unexpected signal code 5** 結束。臨時測試原始碼及產生的畸形檔已移除。

修正方向：所有讀取位置、大小及累加統計使用有溢位檢查的運算，在配置記憶體或尋址前驗證上下界，將壞檔案統一轉為可處理的解析錯誤。
