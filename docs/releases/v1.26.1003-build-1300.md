## 繁體中文

本版降低 TCP Ring 等待網路資料時的 CPU 負擔，持續排查實體雙 Mac 推論逾時。

### 變更與升級

- MLX socket 暫時無法收送時改用 `poll` 等待事件；I/O 與等待不持有佇列鎖，接收等待中仍可加入傳送工作。保留原有佇列同步、斷線回收、錯誤診斷及運算期限。
- 同項等待測試中，等待 1 秒的程序 CPU 時間由約 1.006 秒降至 0.011 秒。此數字只代表等待成本，不能當作模型推論加速比。
- 所有節點需更新完整 App／Server 與同一份 `rdma7` Runtime，使用相同模型檔案及相對路徑，再重新探索、配對。不可混用 `rdma6` 或更早成品。
- TCP Ring 維持 2–8 節點、safetensors 文字推論，包含 Qwen3.5 的通用線性層分片；GGUF、圖片、DFlash 與 MTP 不適用。探索及通訊適用可信任區網，通道未加密；模型 API 白名單不等於遠端管理登入。

### 驗證與已知限制

ThreadSanitizer 並行收送、等待中新增相反方向工作、雙向斷線及 TCP 錯誤／回收 Smoke 通過。原生三 Rank 與同機三個獨立 Server 的探索、交握、推論、串流、故障及租約回收通過。同機兩個 Server 執行 Qwen3.5-4B 真實模型，中英文內容及 Token 數與單機一致，SSE 與停止回收通過。

2026-10-03 發布後補測：M4 Pro／64 GB 與 M4／16 GB 經 5 GHz Wi-Fi 完成原生 TCP 與模型校驗，但完整雙機推論仍未通過。Qwen3 請求超過 240 秒；Qwen3.5 SSE 約 12.5 秒出現第一個內容，到 180 秒仍未完成。遠端單機短回覆正常，保持視窗在最前方也未排除雙機逾時。停止模型後，一般 HTTP 圖檔下載亦重現約 500 bytes/s 的間歇降速；後續同一路徑又完整傳完約 138 MB，尚未確認根因。每層通訊仍有成本，不保證雙機加速；Thunderbolt JACCL RDMA 尚未實測。[最新實測與可重跑的診斷方式](https://github.com/VaderChen/Tanpopo/blob/main/docs/MLX-RDMA.md#user-content-wifi-validation-1300)。

build 1227 與 1300 自動更新後曾出現 HTTP／探索正常、原生 TCP 卻回報 `No route to host`。若遇到相同現象，請完整結束 Tanpopo，再從「應用程式」開啟後重新配對，不需重複下載。啟動方式差異的系統原因仍待確認，本版未修改更新啟動方式。

macOS 發行包完成簽章、公證、Gatekeeper 與隔離更新 Smoke；Windows、Linux 已建置封裝，完整安裝仍待各平台驗證。詳見 [分散推論指南](https://github.com/VaderChen/Tanpopo/blob/v1.26.1003-build-1300/docs/MLX-RDMA.md)。

## English

This release reduces CPU use while TCP Ring waits for network data. Investigation of physical two-Mac inference timeouts continues.

### Changes and upgrade

- MLX sockets use `poll` when they cannot make I/O progress. Neither I/O nor waiting holds the queue lock, so send work can be added during a pending receive. Queue synchronization, disconnect cleanup, diagnostics, and operation deadlines remain in place.
- In the same waiting test, process CPU time during a one-second wait fell from about 1.006 seconds to 0.011 seconds. This measures waiting overhead, not model inference speedup.
- Update the complete App/Server and identical `rdma7` Runtime on every node, use identical model files and relative paths, then discover and pair again. Do not mix with `rdma6` or earlier builds.
- TCP Ring remains limited to 2–8 nodes and safetensors text inference, including generic linear sharding for Qwen3.5. GGUF, images, DFlash, and MTP are excluded. Discovery and unencrypted traffic are for trusted LANs. The model API IP allowlist does not grant remote administrator access.

### Validation and known limits

ThreadSanitizer concurrent I/O, adding opposite-direction work while waiting, bidirectional disconnects, and TCP error/cleanup smoke tests passed. Native three-rank tests and three independent Servers on one Mac passed discovery, handshake, inference, streaming, failure recovery, and lease cleanup. Two Servers on one Mac passed real Qwen3.5-4B English/Chinese output and token comparisons, SSE, and stop cleanup.

Post-release tests on 2026-10-03: an M4 Pro/64 GB and M4/16 GB over 5 GHz Wi-Fi passed native TCP setup and model verification, but full two-Mac inference still failed validation. Qwen3 exceeded 240 seconds. Qwen3.5 SSE produced its first content at about 12.5 seconds but did not finish within 180 seconds. Remote single-node short replies worked; keeping the window in front did not resolve the two-node timeout. With models stopped, ordinary HTTP image downloads also intermittently slowed to about 500 bytes/s; a later run over the same path completed about 138 MB. The root cause remains unconfirmed. Per-layer communication remains costly; two-node speedups are not guaranteed, and Thunderbolt JACCL RDMA remains untested. See [updated measurements and repeatable diagnostics](https://github.com/VaderChen/Tanpopo/blob/main/docs/MLX-RDMA.md#user-content-wifi-validation-1300) in Traditional Chinese.

After automatic updates to builds 1227 and 1300, HTTP/discovery worked while native TCP reported `No route to host`. If this occurs, fully quit Tanpopo, reopen it from Applications, and pair again; no repeated download is needed. The system cause of the launch-path difference remains unconfirmed. This release does not change update relaunch behavior.

macOS packages passed signing, notarization, Gatekeeper, and isolated update smoke tests. Windows and Linux packages were built; full installation still requires validation on those platforms. See the [distributed inference guide](https://github.com/VaderChen/Tanpopo/blob/v1.26.1003-build-1300/docs/MLX-RDMA.md) in Traditional Chinese.

## 日本語

本版では TCP Ring がネットワークデータを待つ間の CPU 負荷を軽減しました。実機 Mac 2 台の推論タイムアウトは引き続き調査中です。

### 変更と更新条件

- MLX socket が送受信を進められない場合は `poll` でイベントを待ちます。I/O と待機中はキューロックを保持せず、受信待ちの間も送信を追加できます。キュー同期、切断回収、診断、演算期限は維持します。
- 同じ待機テストで、1 秒の待機中のプロセス CPU 時間は約 1.006 秒から 0.011 秒に減りました。待機コストの測定であり、モデル推論の高速化率ではありません。
- 全ノードの App/Server と同一の `rdma7` Runtime を更新し、同一のモデルファイルと相対パスを使って再検索・ペアリングしてください。`rdma6` 以前との混在はできません。
- TCP Ring は引き続き 2–8 ノードの safetensors テキスト推論に対応し、Qwen3.5 の汎用線形層分割を含みます。GGUF、画像、DFlash、MTP は対象外です。探索と暗号化されない通信は信頼できる LAN で使用してください。モデル API の IP 許可リストはリモート管理権限を付与しません。

### 検証と既知の制限

ThreadSanitizer による並行送受信、待機中の逆方向の処理追加、双方向切断、TCP エラー／回収 Smoke に合格しました。ネイティブ 3 Rank と同一 Mac 上の独立した 3 Server で探索、ハンドシェイク、推論、ストリーミング、障害・リース回収を確認しました。同一 Mac 上の 2 Server で実際の Qwen3.5-4B の英語・中国語出力と Token 数が単独実行と一致し、SSE と停止回収にも合格しました。

2026-10-03 の公開後テスト：M4 Pro／64 GB と M4／16 GB を 5 GHz Wi-Fi で接続し、ネイティブ TCP とモデル照合には成功しましたが、完全な 2 台推論の検証には未合格です。Qwen3 は 240 秒を超過し、Qwen3.5 SSE は約 12.5 秒で最初の内容を返したものの 180 秒以内に完了しませんでした。リモート単独での短い応答は正常で、ウィンドウを最前面にしても 2 台推論のタイムアウトは解消しませんでした。モデル停止中の通常の HTTP 画像ダウンロードでも約 500 bytes/s への間欠的な低下を再現しましたが、その後同じ経路で約 138 MB を完了した例もあり、根本原因は未確認です。層ごとの通信コストがあり、2 台での高速化は保証しません。Thunderbolt JACCL RDMA は未実測です。繁体字中国語の [最新の実測と再実行可能な診断方法](https://github.com/VaderChen/Tanpopo/blob/main/docs/MLX-RDMA.md#user-content-wifi-validation-1300) を参照してください。

build 1227 と 1300 の自動更新後、HTTP／探索は正常でもネイティブ TCP が `No route to host` を返す現象がありました。同じ場合は Tanpopo を完全終了し、「アプリケーション」から開いて再ペアリングしてください。再ダウンロードは不要です。起動方法による差のシステム内部原因は未確認で、本版は更新後の起動方式を変更していません。

macOS パッケージは署名、公証、Gatekeeper、隔離更新 Smoke に合格しました。Windows と Linux はビルド・パッケージ作成済みですが、完全なインストール検証は各環境で必要です。詳細は繁体字中国語の [分散推論ガイド](https://github.com/VaderChen/Tanpopo/blob/v1.26.1003-build-1300/docs/MLX-RDMA.md) を参照してください。

## 한국어

이번 릴리스는 TCP Ring이 네트워크 데이터를 기다리는 동안 CPU 사용량을 줄입니다. 실제 Mac 두 대의 추론 시간 초과는 계속 조사 중입니다.

### 변경 사항과 업데이트 조건

- MLX socket이 송수신을 진행할 수 없으면 `poll`로 이벤트를 기다립니다. I/O와 대기 중에는 큐 잠금을 유지하지 않아 수신을 기다리면서 송신 작업을 추가할 수 있습니다. 큐 동기화, 연결 끊김 정리, 진단과 연산 제한 시간은 유지합니다.
- 동일한 대기 테스트에서 1초 대기 중 프로세스 CPU 시간이 약 1.006초에서 0.011초로 감소했습니다. 이는 대기 비용이며 모델 추론 속도 향상 비율이 아닙니다.
- 모든 노드의 전체 App/Server와 동일한 `rdma7` Runtime을 업데이트하고 같은 모델 파일과 상대 경로로 다시 검색·페어링하세요. `rdma6` 또는 이전 버전과 혼용할 수 없습니다.
- TCP Ring은 계속 2–8개 노드의 safetensors 텍스트 추론을 지원하며 Qwen3.5의 범용 선형 레이어 분할을 포함합니다. GGUF, 이미지, DFlash, MTP는 제외됩니다. 검색과 암호화되지 않은 통신은 신뢰할 수 있는 LAN용입니다. 모델 API IP 허용 목록은 원격 관리자 권한을 부여하지 않습니다.

### 검증과 알려진 제약

ThreadSanitizer 동시 송수신, 대기 중 반대 방향 작업 추가, 양방향 연결 끊김, TCP 오류/정리 Smoke를 통과했습니다. 네이티브 3 Rank와 한 Mac의 독립 Server 3개에서 검색, 핸드셰이크, 추론, 스트리밍, 장애·임대 정리를 확인했습니다. 한 Mac의 Server 두 개에서 실제 Qwen3.5-4B의 영어·중국어 출력과 Token 수가 단독 실행과 같았으며 SSE와 종료 정리도 통과했습니다.

2026-10-03 공개 후 테스트: M4 Pro/64 GB와 M4/16 GB를 5 GHz Wi-Fi로 연결하여 네이티브 TCP 연결과 모델 검증은 통과했지만, 완전한 두 Mac 추론 검증은 통과하지 못했습니다. Qwen3 요청은 240초를 넘겼고, Qwen3.5 SSE는 약 12.5초에 첫 내용을 반환했으나 180초 이내에 완료되지 않았습니다. 원격 단독 실행의 짧은 응답은 정상이었고 창을 맨 앞으로 유지해도 두 노드 시간 초과는 해소되지 않았습니다. 모델을 정지한 상태의 일반 HTTP 이미지 다운로드에서도 약 500 bytes/s로 간헐적으로 느려지는 현상을 재현했지만, 이후 같은 경로에서 약 138 MB를 완료한 사례도 있어 근본 원인은 미확인입니다. 레이어별 통신 비용이 있으며 두 노드의 속도 향상을 보장하지 않습니다. Thunderbolt JACCL RDMA도 아직 실측하지 않았습니다. 중국어 번체 [최신 실측 및 재실행 가능한 진단 방법](https://github.com/VaderChen/Tanpopo/blob/main/docs/MLX-RDMA.md#user-content-wifi-validation-1300)을 참고하세요.

build 1227과 1300 자동 업데이트 뒤 HTTP/검색은 정상인데 네이티브 TCP가 `No route to host`를 반환한 경우가 있었습니다. 같은 현상이 발생하면 Tanpopo를 완전히 종료한 뒤 응용 프로그램에서 다시 열어 페어링하세요. 다시 다운로드할 필요는 없습니다. 시작 방식에 따른 차이의 시스템 내부 원인은 미확인이며 이번 버전은 업데이트 후 시작 방식을 변경하지 않습니다.

macOS 패키지는 서명, 공증, Gatekeeper, 격리된 업데이트 Smoke를 통과했습니다. Windows와 Linux 패키지는 빌드했으며 전체 설치는 각 플랫폼에서 추가 검증이 필요합니다. 중국어 번체 [분산 추론 가이드](https://github.com/VaderChen/Tanpopo/blob/v1.26.1003-build-1300/docs/MLX-RDMA.md)를 참고하세요.
