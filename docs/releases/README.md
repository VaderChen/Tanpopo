# Release 撰寫與更新規則

每版公開發行說明存放於 `v<版本>-build-<編號>.md`，以 `gh release create/edit --notes-file` 原樣同步到 GitHub。

- GitHub Release 名稱使用 `Tanpopo <版本> build <編號>`。內文不要再放相同版本標題或第一級標題，避免頁面重複顯示。
- 內文先放語言導覽，依序提供 `## 繁體中文`、`## English`、`## 日本語`、`## 한국어`；每種語言的主題使用第三級標題。Release 內文不會自動產生標題錨點，須在各語言標題前明確加入 `<a name="zh-tw"></a>`、`en`、`ja`、`ko` 對應錨點。GitHub 渲染後會加上 `user-content-` 前綴，導覽須連到實際錨點，例如 `#user-content-zh-tw`。
- 四種語言須涵蓋相同的功能變更、升級條件、相容性與安全限制、實際驗證範圍、下載檔案。未驗證事項不得在翻譯時改寫為已支援或已測試。
- 指令、Runtime 版本、檔名、API 路徑及連結保持一致；需要說明介面按鈕時，保留實際畫面標籤供對照。
- 數字範圍使用 `–`（例如 `2–8`），避免多個未跳脫的半形 `~` 被 GitHub Markdown 誤判為刪除線。
- 純文字或翻譯更正更新既有 Release 內文及主分支文件，不移動已發布標籤、不替換安裝包或變更 SHA-256。程式或安裝包需要變更時使用新版本／build。

大量修改前先建立 `.bak`。發布前檢查 Markdown 語法、四語內容與語言導覽，使用 GitHub Markdown 預覽確認沒有重複版本標題或意外刪除線。發布後實際點選語言導覽，並比對遠端內文與本機文件，確認版本標籤、目標 commit 及附件摘要，驗收通過後再移除備份。
