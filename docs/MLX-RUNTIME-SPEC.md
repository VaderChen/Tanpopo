# MLX Runtime 規格

## 並行容量

核心 SPEC 是「支援多人並行」。**目前階段先將上限定為 4 人**，並非永久固定只能支援四人。容量以同一 Runtime 中進行中的生成請求計算，非串流與串流請求共用名額；不得以修正長輸入或記憶體問題為由改成單人服務。

並行上限集中管理，名額計算、忙碌提示及資源預算均依該上限運作，供後續階段調整。目前四人上限的行為如下：

- 四個請求各自持有 KV Cache、decoder state、取消狀態與錯誤通知，不得互相覆寫。
- 名額未滿且資源檢查通過時可接受請求；第 5 個生成請求回傳 HTTP 429，不中斷既有四個請求。
- 名額涵蓋輸入準備、Prefill 與生成。worker 完成、失敗或取消後釋放名額；準備階段失敗也不得遺留名額。
- 共用預留帳本以原子步驟計算並保留每個請求的 KV 與暫存預算，避免四個請求重複使用同一份可用記憶體。釋放名額時一併釋放預算。
- 多人容量不表示可以超越實體記憶體或裝置限制。超出資源預算時需回傳明確錯誤，不得崩潰、無限等待，或默默縮短上下文。

## 長輸入處理

支援分段的模型路徑必須遵守實際 Prefill 分段大小。token、embedding、mask、位置資訊及 decoder state 必須保持一致；每段應完成必要求值，避免 lazy graph 累積整份長輸入的中間結果。

在 tokenization 後、模型 forward 前檢查輸入與最大輸出 token 數，以及依模型 metadata 與裝置能力估算的記憶體需求。資源不足時可縮小本次分段大小，不得改寫使用者設定或校準紀錄。未宣告分段能力的模型路徑按整份輸入保守估算。

## 錯誤與服務存活

- 上下文或預估記憶體超限：非串流回傳 HTTP 413；串流已建立時改送 SSE error。
- 四個名額已滿：HTTP 429。
- 推論中超過記憶體預算：非串流回傳 HTTP 503。
- 可攔截的 MLX 運算／配置錯誤：非串流回傳 JSON error；串流已開始時送出 SSE error 及結束標記，不回報成功完成。
- 單次請求失敗不得因 MLX 預設 fatal error handler 而直接終止整個服務。作業系統強制終止與不可恢復的 GPU 驅動故障不在應用程式可保證攔截的範圍。
- 日誌記錄請求受理、token 數、實際分段與資源估算，不記錄提示內容。

## 串流回應時機

`stream: true` 在完成請求格式、模型與生成名額檢查後，即建立 SSE 回應，不等待 Tokenization、Prefill 或首個生成 token。四個名額已滿時仍在送出 SSE header 前回傳 HTTP 429。

- 連線建立後立即送出 SSE 保活註解；之後每 10 秒送出一次，直到回應完成、取消或連線失敗。保活由 HTTP event loop 排程，不依賴模型工作的執行進度；連線不可寫時不繼續堆積保活資料。
- Chat Completion 保留標準的首個 assistant role chunk；實際文字與工具事件仍隨生成逐段輸出，不以保活或空白內容冒充模型輸出。
- Prefill 尚未完成時可能沒有思考／回答文字；保活只能確認連線仍存活，不代表首 token 延遲已消除。
- SSE 建立後的輸入準備、上下文／記憶體檢查與生成錯誤以 SSE error 結束，不再嘗試改寫 HTTP 狀態或回報成功完成。

## 對應請求的取消

每個 HTTP 請求持有獨立的取消訊號與識別碼，並由輸入準備、Prefill、生成及串流轉接共用。不得只停止回應輸出，卻讓模型的衍生 Task 繼續運算。

- 連線關閉、連線錯誤或 HTTP 工作被取消時，直接設定該請求的取消訊號；不能只依賴 AsyncStream 的取消逐層傳遞。
- 等待回應期間必須持續讀取 socket，讓 Prefill、非串流與串流中的斷線皆能及時被察覺；不得使用「等待整份回應完成才恢復讀取」的 HTTP pipelining 背壓。
- 同一 HTTP/1 連線的請求依序回應，後續請求不得取代或取消目前工作。等待佇列最多 4 筆，等待中的 body 與正在接收的 body 合計不得超過單次請求大小上限；超限只關閉該連線並取消其工作。這是單連線緩衝限制，不是多人生成名額。一般 Keep-Alive 繼續支援，`Connection: close` 在當次回應結束後關閉。
- 串流提前結束、命中 stop 或消費者離開時，也必須通知對應的模型工作。
- 分段 Prefill 在段落邊界檢查取消，生成在每次迭代前檢查。已提交給 GPU 的 kernel 不強制中斷；等待在途運算收尾後，釋放該工作與預留資源。
- 取消一個請求不得停止 Runtime、清除其他請求的快取，或影響其他使用者的生成。其他請求仍在運算時，整體 GPU 使用率不必降到零。
- 日誌中的 `request_id` 用於對照請求開始、HTTP 取消與名額釋放，不記錄提示內容。

外部程式直接呼叫 8080 時，「強制結束」必須實際中斷 HTTP 請求／回應串流。若客戶端只停止畫面顯示，仍維持原請求，Runtime 無法從介面狀態得知應取消工作。

## 推論驗收項目

在資源足夠的環境中，需以實際推論確認四個請求可同時進行、第 5 個得到 429、完成／取消／失敗後可再次接收請求，且長上下文或配置失敗不造成服務退出。語法與編譯通過不等同於上述推論驗收通過。

取消驗收需涵蓋 Prefill 中斷線、生成中斷線、尚未開始讀取 SSE 即斷線、非串流請求取消及命中 stop；取消其中一個工作時，其他並行工作應能繼續完成。HTTP 驗收還需涵蓋 Keep-Alive 重用、同連線 pipelining 回應順序與緩衝超限。

長 Prefill 的串流驗收應分別記錄 SSE header／首個 chunk 與首個實際生成 token 的時間；等待期間應持續收到保活註解，取消後不得再啟動尚未開始的生成工作。

目前已完成語法與 Release 組態編譯檢查，不等同於上述推論驗收已全部完成。通用診斷方法見 [API 延遲與取消排查](MLX-RUNTIME-TROUBLESHOOTING.md)。
