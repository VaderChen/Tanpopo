本表保留整合 recurrent controls、tensor 契約驗證與新版快取前的基線數據；主系統完成這些修正後， fastGGUF 已成為多數可解析 GGUF 的建議預設。模型架構、量化方式、Tokenizer 與自訂 checkpoint 仍可能影響結果，因此不能把 fastGGUF 視為唯一執行手段；正式使用前應逐模型驗證速度與精確度， 並保留原生 MLX 或 llama+GGUF 作為相容路徑。

Actual product parameters

fastGGUF 開關實際策略

表內速度與精度是整合 recurrent controls 前的基線；主系統現行 fastGGUF 另將控制投影保留 BF16，整合後數據需重新量測。

模式參數主要權重定位
純 MLX原生 checkpointAffine 4-bit／group 64速度與品質基準
fastGGUF 關閉auto + group 32Q4 等低位元來源重新量化為 INT8較保守，但不是保真模式
fastGGUF 開啟speed + group auto + recurrent controls低位元矩陣轉為 INT4；控制投影保留 BF16實驗性速度／精度折衷

品質閘門定義

fastGGUF 精度不得比同一 GGUF 的 llama 參考低超過 2 個百分點，無效答案不得多超過 1 題。 逐題一致率只作診斷，不直接當門檻。本輪 6 個 fastGGUF 組合全部失敗；27B 抽查可見連續標點輸出， 證實無效答案不是評分器漏抓 A–D。

Experimental follow-up

Recurrent controls POC

已整合為 fastGGUF 的實驗策略，預設仍關閉。

只提升 alpha／beta 控制投影可改善 4B，但仍未過門檻

先前以 Qwen 3.5 4B 將 Gated Delta／SSM 的 alpha、beta 投影升為 BF16，固定 100 題由 fastGGUF 基線 41% 提升到 59%，無效答案由 29 降至 3，生成維持約 73.6 tok/s；但仍比 llama 參考 72% 低 13 點。 此改善不足以讓 fastGGUF 預設開啟，因此只在使用者明確啟用時，以 tensor 語意角色通用套用；後續仍需擴充誤差敏感度與架構合約。

POC 彙總：fastgguf-poc-results.csv；主系統參數為 --gguf-recurrent-promotion controls。

Methodology

測試方法與限制

速度

  • OpenAI 相容 /v1/chat/completions
  • 46 prompt tokens、128 completion tokens
  • Temperature 0、Top-K 1、thinking 關閉
  • 暖機 1 次；正式 3 次採中位 tok/s

精度

  • OpenAI Simple Evals MMLU CSV
  • 固定 100 題、seed 0
  • 每個模型與模式使用完全相同題目
  • 只接受獨立 A、B、C、D；其餘為無效

共同 Runtime

  • 兩個 Runtime 均使用 Release build
  • MLX+GGUF 明確傳入 --mmap；純 MLX 未傳入
  • KV cache 上限 4096 tokens
  • 未啟用 DFlash 與 KV Cache 量化
  • llama：Metal 全層、Flash Attention、8 threads

解讀限制

  • 三個模型是通用策略的抽樣證據，不是支援白名單
  • 載入時間未清除系統檔案快取
  • 程序 RSS 不等於系統統一記憶體總量
  • Runtime 或 Metal 更新後應重新測試

速度彙總：benchmark-results.csv · 精度彙總：accuracy-summary.csv · 重現腳本：run-benchmark.sh、 run-accuracy-benchmark.sh

Recommendation

目前建議

正式使用優先純 MLX

若有可信原生 MLX checkpoint，這仍是本輪速度、載入、RSS 與精度最完整的路徑。

GGUF 先回退 llama

llama+GGUF 在三模型都維持有效答案與合理精度，且不需支付 MLX 重新量化的載入成本。

fastGGUF 保持實驗旗標

速度目標已達成，但不可只因模型能載入就開放；至少應通過模型級 smoke quality gate 才能啟用。

下一步是數值合約

建立逐層漂移、logit 一致性、敏感 tensor 提升與自動回退，讓策略依 tensor／架構能力決定，而非模型名稱。
