目前 fastGGUF 已推薦使用，但不能視為唯一手段，仍需驗證相容性

fastGGUF 對三個樣本平均帶來 1.73×（相對關閉）的生成速度，適合在模型通過品質驗證後使用。 但本輪三個 fastGGUF 開啟結果皆未保留純 MLX 精確度的 90%，證明模型架構、量化方式、Tokenizer 與自訂 checkpoint 仍會影響結果。它是建議嘗試的加速手段，不是唯一手段，也不保證每個 GGUF 都相容；正式使用應保留原生 MLX 或 llama+GGUF 作為回退路徑。

品質閘門定義

快速策略必須至少保留同模型純 MLX 精確度的 90%；無效答案會自然計入錯誤，不另外美化。 llama+GGUF 保留為相同 GGUF 的獨立參考。本輪 6 個 MLX+GGUF 組合皆未過門檻，其中 27B fastGGUF 開啟達 78/100、保留 87.6%，最接近但仍不採用「以速度優先」的判定。

Experimental follow-up

Recurrent controls POC

控制投影提升已納入本輪 fastGGUF 開啟測試，但不能單獨保證模型品質。

recurrent controls 仍需配合模型級品質驗證

本輪以相同 100 題重測整合後策略，fastGGUF 開啟在 Qwen 3.5 4B、Ornith 1.5 9B、Qwen 3.8 27B 分別取得 37%、0%、78%，只有 27B 接近門檻。另測「INT4、Group 自動、recurrent 關閉」也只有 50% 與 1%（4B／9B），說明問題不是單一開關即可解決。後續必須依 tensor 語意角色、架構合約 與小型品質閘門共同決定是否啟用，而不是依模型名稱寫特例。

POC 彙總：fastgguf-poc-results.csv；主系統參數為 --gguf-recurrent-promotion controls。

Methodology

測試方法與限制

速度

  • OpenAI 相容 /v1/chat/completions
  • 46 prompt tokens、128 completion tokens
  • Temperature 0、Top-K 1、thinking 關閉
  • 暖機 1 次；正式 3 次採中位 tok/s

精度

  • OpenAI Simple Evals MMLU CSV
  • 固定 100 題、seed 0
  • 每個模型與模式使用完全相同題目
  • 只接受獨立 A、B、C、D；其餘為無效

共同 Runtime

  • 兩個 Runtime 均使用 Release build
  • MLX+GGUF 明確傳入 --mmap；純 MLX 未傳入
  • 速度量測以 --no-gguf-cache 排除快取壓縮與寫入
  • KV cache 上限 4096 tokens
  • 未啟用 DFlash 與 KV Cache 量化
  • llama：Metal 全層、Flash Attention、8 threads

解讀限制

  • 三個模型是通用策略的抽樣證據，不是支援白名單
  • 載入時間未清除 macOS 系統檔案快取
  • 程序 RSS 不等於系統統一記憶體總量
  • Runtime 或 Metal 更新後應重新測試

速度彙總：benchmark-results.csv · 精度彙總：accuracy-summary.csv · 重現腳本：run-benchmark.sh、 run-accuracy-benchmark.sh

Recommendation

目前建議

正式使用優先純 MLX

若有可信原生 MLX checkpoint，這仍是本輪速度、載入、RSS 與精度最完整的路徑。

GGUF 先回退 llama

llama+GGUF 在三模型都維持有效答案與合理精度，且不需支付 MLX 重新量化的載入成本。

fastGGUF 通過閘門後使用

建議嘗試 fastGGUF，但必須先保留至少 90% 的同模型純 MLX 精確度；未通過時應自動或手動回退。

下一步是數值合約

建立逐層漂移、logit 一致性、敏感 tensor 提升與自動回退，讓策略依 tensor／架構能力決定，而非模型名稱。
